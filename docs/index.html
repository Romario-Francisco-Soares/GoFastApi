Framework HTTP para Go

GoFastAPI.

Uma experiência de desenvolvimento inspirada no FastAPI, construída sobre net/http. Rotas expressivas, contexto, middleware, DI e OpenAPI — com interoperabilidade com o ecossistema Go.

Estado do projeto — em desenvolvimento. Esta documentação descreve o código implementado neste snapshot. GoFastAPI não oferece paridade integral com FastAPI/Uvicorn; recursos parciais e ausentes estão identificados nesta página e no SDD.
net/httpBase HTTP nativa do Go
TrieRotas dinâmicas indexadas por segmento
3 scopesSingleton, Request e Transient

Visão geral

GoFastAPI procura remover boilerplate sem esconder o modelo de execução do Go. A aplicação pode ser utilizada como framework ou integrada em um servidor existente por meio de app.Handler(), que retorna um http.Handler.

Experiência de alto nível

Registro declarativo de rotas, respostas, dependências, grupos e metadados OpenAPI.

Interoperabilidade

Handlers e middleware continuam compatíveis com interfaces padrão da biblioteca HTTP do Go.

Eficiência consciente

Context lazy e handlers idiomáticos sem reflexão no hot path. Handlers genéricos tipados usam reflexão em execução.

Operação integrada

Servidor, TLS single-process, graceful shutdown, health checks e supervisor multiprocesso com limites conhecidos.

Quick start

Este repositório usa atualmente module gofast. A aplicação abaixo compila dentro deste módulo. Antes de publicar, substitua o caminho do módulo por seu endereço canônico.

package main

import (
    "log"
    gofast "gofast"
)

func main() {
    app := gofast.New(
        gofast.Title("Minha API"),
        gofast.Version("1.0.0"),
        gofast.Description("Serviço HTTP de exemplo"),
    )

    app.GET("/", func(ctx *gofast.Context) (any, error) {
        return gofast.OK(map[string]string{"message": "Hello World"}), nil
    })

    app.GET("/items/{id}", func(ctx *gofast.Context) (any, error) {
        return gofast.OK(map[string]string{
            "id": ctx.Param("id"),
            "q":  ctx.Query("q"),
        }), nil
    })

    cfg := gofast.DefaultServerConfig()
    cfg.Addr = ":8000"
    if err := app.Run(cfg); err != nil {
        log.Fatal(err)
    }
}

Execute o exemplo no repositório com go run ./cmd/server. Por padrão a aplicação registra:

Rotas e grupos

App aceita GET, POST, PUT, PATCH, DELETE, OPTIONS, HEAD, TRACE e WebSocket. O sub-router oferece GET, POST, PUT, DELETE e AddRoute.

router := gofast.NewRouter()
users := router.Group("/users", gofast.GroupTags("users"))

users.GET("/{id}", func(ctx *gofast.Context) (any, error) {
    return gofast.OK(map[string]string{"id": ctx.Param("id")}), nil
})

app.Include(router, gofast.IncludeOption{Prefix: "/v1"})
app.Mount("/static", gofast.NewStaticFiles("./public"))
  • Rotas estáticas usam índice por método/caminho.
  • Rotas dinâmicas usam trie por segmento.
  • {id} captura segmento único; {filepath:path} captura o restante.
  • GET responde HEAD com o corpo suprimido.
  • 405/Allow é gerado quando caminho existe, mas o método não.

Não há DSL completa de conversores como int/UUID/datetime, nem política configurável de barra final nesta versão.

Context e binding

O Context oferece Request(), ResponseWriter(), Context(), Param(), Query(), Header(), Cookie(), Session(), State(), Resolve(), JSON(), Body(), FormValue(), FormFile(), RemoteAddr() e métodos de escrita.

type CreateItem struct {
    Name string `json:"name"`
}

func (p *CreateItem) Validate() error {
    if strings.TrimSpace(p.Name) == "" {
        return errors.New("name is required")
    }
    return nil
}

app.POST("/items", func(ctx *gofast.Context, input CreateItem) (any, error) {
    return gofast.Created(map[string]string{"name": input.Name}), nil
})

O binding tipado suporta um corpo JSON por handler com struct/map/slice/interface conforme a assinatura compilada e permite Validate() error. Assinaturas genéricas fazem reflect.Call em cada requisição. Binding manual permanece disponível pelos helpers do Context.

Não é Pydantic: tags arbitrárias, aliases, defaults e binding automático integral de header/cookie/form/file ainda não estão implementados.

Injeção de dependências

type UserService struct{}
func NewUserService() *UserService { return &UserService{} }

app.Provide(NewUserService, gofast.Singleton())

app.GET("/me", func(ctx *gofast.Context, svc *UserService) (any, error) {
    return gofast.OK(map[string]string{"state": "ready"}), nil
}, gofast.RouteOption{
    Dependencies: []gofast.Depends{{Dependency: (*UserService)(nil)}},
})
EscopoSemântica
Singleton()Uma instância por container/processo, inicialização lazy sincronizada.
Request()Uma instância por Context/requisição.
Transient()Nova instância por resolução.

Providers podem retornar T, (T, error), (T, func()) ou (T, func() error). Dependências cíclicas são detectadas. Cleanups request/transient são executados ao fim da requisição e cleanups singleton no fechamento da aplicação. Overrides devem ocorrer durante o startup/configuração.

Respostas e erros

Tipos disponíveis: JSON (`OK`, `Created`, `NewJSONResponse`), texto, HTML, arquivo, redirect, stream e resposta vazia. A interface é Response; não existe Response[T].

app.GET("/redirect", func(ctx *gofast.Context) (any, error) {
    return gofast.NewRedirectResponse("/docs", http.StatusTemporaryRedirect), nil
})

app.GET("/private", func(ctx *gofast.Context) (any, error) {
    return nil, gofast.NewHTTPError(403, "forbidden", "access denied")
})

Erros podem ser tratados com HTTPError, ValidationError e app.OnError(typeOrPredicate, handler).

Sessões e segurança

Cookie de sessão AES-GCM

app.Use(gofast.SessionMiddleware(gofast.SessionConfig{
    Secret: os.Getenv("SESSION_SECRET"),
    CookieName: "session",
    HTTPOnly: true,
    Secure: true,
    SameSite: http.SameSiteLaxMode,
}))

A sessão é stateless e armazenada em cookie autenticado/cifrado AES-GCM, limitada em tamanho. Use segredo aleatório e de alta entropia, fora do repositório. Em produção HTTPS, configure Secure/HTTPOnly/SameSite conforme seu modelo de ameaça.

Autenticação

O pacote raiz fornece APIKey (header/query/cookie), HTTPBearer, HTTPBasic e OAuth2Bearer com callbacks de validação. Os dados do usuário autenticado ficam em ctx.Principal().

Não há servidor OAuth2, emissão de JWT, refresh tokens ou autenticação OIDC completa. A validação de tokens é delegada a um provedor/callback externo.

OpenAPI e documentação

app.OpenAPI() gera um objeto OpenAPI 3.1 básico. Use RouteOption para informar tags, summary, description, operation ID, responses, deprecated e security. Registre schemes com app.AddSecurityScheme.

Rotas internas: /openapi.json, /docs e /redoc.

Schema limitado: a biblioteca ainda não infere completamente request/response schemas dos tipos Go. ResponseModel não gera JSON Schema automaticamente; callbacks, webhooks e exemplos automáticos não estão implementados.

WebSocket e streaming

WebSocket oferece handshake/upgrade e frames básicos de texto, binário, JSON, ping/pong, close, limites e deadlines. Não há fragmentação completa, subprotocolos, extensões de compressão nem política de Origin configurável integrada.

SSE e streaming genérico são fornecidos por SSE, SSEWithHeartbeat, WriteEvent, Stream e StreamWithContentType. Em deploy, ajuste os timeouts do servidor e do reverse proxy para conexões longas.

Background tasks

app.POST("/emails", func(ctx *gofast.Context) (any, error) {
    ctx.BackgroundTasks().Add(func() {
        // tarefa curta após o flush da resposta
    })
    return gofast.OK(map[string]bool{"queued": true}), nil
})

As tarefas são em processo, executadas sequencialmente após o flush da resposta no ciclo de atendimento. Erros/panics são logados. Não existe persistência, retry durável ou distribuição; utilize uma fila externa para tarefas críticas.

Health checks

app.Health().RegisterChecker("database", func() error {
    return db.PingContext(context.Background())
})

// Marque readiness conforme o lifecycle da aplicação.
app.OnStart(func(ctx context.Context) error {
    app.Health().SetReady(true)
    return nil
})

/health/live verifica liveness; /health/ready consulta readiness e checkers registrados. Checkers externos devem ser rápidos e aplicar seus próprios timeouts.

Servidor e configuração

cfg := gofast.DefaultServerConfig()
cfg.Addr = ":8000"
cfg.ReadHeaderTimeout = 5 * time.Second
cfg.IdleTimeout = 75 * time.Second
cfg.GracefulTimeout = 30 * time.Second
cfg.Workers = 1

if err := app.Run(cfg); err != nil {
    log.Fatal(err)
}

Single-process usa net/http.Server, bloqueia até shutdown/erro, suporta TCP/UDS/FD, TLS e mTLS, timeouts HTTP, keep-alive, limites, proxy headers e trusted hosts. App.Serve(ctx, listener) permite listener externo e cancelamento por contexto.

Workers e Supervisor

Com Workers > 1, o Supervisor inicia processos filhos, herda o listener por file descriptor e usa um pipe de prontidão (FD 4) antes de considerar o worker iniciado. Oferece restart policy, backoff, limite de reinicializações, PID file, limite de requests e shutdown controlado.

O health monitor atual verifica se o processo ainda existe (sinal 0). Não há heartbeat periódico nem detecção de processo vivo porém travado. O modo é multiprocesso; não é pool de goroutines. O caminho TLS multiprocesso ainda não está implementado.

CLI integrada

O CLI é executado dentro da aplicação que já foi construída por meio de app.RunCLI(os.Args[1:]) ou gofast.RunCLI(app, args). Ele não é um carregador genérico de projetos a partir de um caminho de arquivo.

ComandoComportamento
runInicia o servidor com endereço, workers e nível de log configuráveis.
devInicia com log debug. Não implementa hot reload.
openapiImprime ou exporta o documento OpenAPI.
routesLista método, caminho e operation ID/summary.
versionExibe a versão reportada pelo CLI.
healthAvalia liveness, readiness e health checkers registrados.
func main() {
    app := buildApp()
    os.Exit(app.RunCLI(os.Args[1:]))
}

Testes e benchmarks

NewTestClient(app) cria um httptest.Server real em loopback, mantém cookies e oferece Get, PostJSON, PostForm, PostMultipart, NewRequest e Do. Não possui client WebSocket/SSE especializado.

go test -race ./...
go vet ./...
go test ./... -cover
go test -run=^$ -bench=. -benchmem

go test -run=^$ -fuzz=FuzzTrieLookup -fuzztime=10s

O projeto contém fuzz targets para extração de parâmetros, parser do rate limit e lookup da trie, além de microbenchmarks para handler nativo e rotas GoFastAPI. Na validação deste snapshot, go test, go test -race e go vet passaram. Cobertura: 33,9% no pacote raiz e 21,3% em middleware. Saturação operacional e queda do processo

Para comparar a degradação, foi adotado um limite operacional de P95 inferior a 100 ms. Esse limite não representa o ponto de crash; ele indica uma referência de latência acima da qual a experiência pode deixar de ser adequada para um serviço sensível a tempo de resposta.

Em 2.048 clientes, as três implementações ultrapassaram o limite de 100 ms. Nenhuma das três apresentou queda de processo confirmada nas rodadas finais. O FastAPI continuou respondendo HTTP 200 após a carga; duas rodadas finais nessa faixa terminaram sem erros de transporte. Uma execução exploratória anterior apresentou falhas de transporte, mas o resultado não se repetiu e não foi classificado como crash confirmado.

Interpretação dos resultados

  • A GoFastAPI atingiu aproximadamente 86% do pico de throughput do Go puro: 54.272 contra 63.210 req/s. A comparação entre picos é aproximada porque ocorreram em concorrências diferentes.
  • Entre concorrências de 1 a 256, a perda média de throughput da GoFastAPI em relação ao Go puro foi de aproximadamente 12,7%.
  • Em 32 clientes, o Go puro alcançou aproximadamente 4,17× o throughput do FastAPI; a GoFastAPI alcançou aproximadamente 3,52×.
  • Em 256 clientes, a GoFastAPI alcançou aproximadamente 3,19× o throughput do FastAPI.
  • A diferença de latência fica mais evidente sob alta concorrência, especialmente a partir de 1.024 clientes.
Como interpretar: estes resultados indicam que, neste endpoint e ambiente, a GoFastAPI preservou boa parte do desempenho do Go nativo. Não devem ser anunciados como uma garantia universal de “X vezes mais rápido” nem como limite de capacidade de produção. Carga real, tamanho do payload, middlewares, DI, TLS, banco de dados, workers, hardware e configuração de rede alteram os resultados.

Esta seção trata de benchmarks HTTP comparativos. Os números de microbenchmarks internos medem chamadas em memória e não devem ser somados ou comparados diretamente com o throughput de rede aqui apresentado.
